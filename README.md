## 一、先说清楚「复刻到什么程度」

这一点很重要，因为它决定了这个项目跟原版是什么关系。

### 1. `ecom-details-image` 不是代码工程，是一套「规则 + 数据」

仓库本体是 Claude Skill 形态，真正的资产是：

| 资产 | 规模 | 作用 |
|---|---|---|
| `SKILL.md` | 30,434 B | 六条铁律、25 个模板的匹配表、Campaign Style Lock 十维度、转化驱动力 A/B/C、多角度镜头规则、详情页信息图铁律 |
| `references/templates/*.json` | 25 个 | 每个模板的 `prompt_template` / `variants` / `category_tips` / `anti_ai_tips`（实测 **88 个变体、66 条示例、66 种 prompt_template 字段**） |
| `scripts/generate_image.py` | 19,041 B | 调 apimart 的 `gpt-image-2`，同步/异步双适配 |
| `apimart.md` + `搭建电商主图详情页补充.md` | 40 KB | 接口细节与实操补充 |

所以「复刻」在这里的正确含义是：**复刻它的规则体系与 Prompt 工程，而不是复刻某个页面的像素**。
本项目把 SKILL.md 里每一条能被机械验证的约束，**逐条翻译成了可断言的代码**（见第六节）。

### 2. 官方 Web UI 是另一个仓，而且它跑不起来

README 里指向的 `liangdabiao/ecom-details-image-ui`（React 18 + Vite 6 + TS + Tailwind v4 + 腾讯云 EdgeOne Makers）
才是"网页应用"的真身。但：

> 🔴 `agents/chat.ts` 第 8 行 `import { TEMPLATES } from "./_templates";` ——
> **仓库里不存在 `agents/_templates.ts`**（已核对完整文件树）。它无法直接构建。

本项目**没有沿用它**，而是自己重建了模板层（`tools/build-templates.mjs` 直接从 Skill 仓的 25 个 JSON 生成），正好绕开这个缺陷。

### 3. 三处刻意的偏离（都是权衡，不是能力不足）

| 维度 | 官方 UI 的做法 | 本项目 | 为什么改 |
|---|---|---|---|
| 编排 | Claude Agent SDK 的 `query()` + 自建 MCP 工具，靠模型主动调 `get_template` / `generate_image` | 确定性代码流水线（`orchestrator.js`） | 20+ 条硬约束靠"模型自觉"必然漂移；改成代码后**能写断言、能复现、没 key 也能用** |
| 模型依赖 | 必须有 Anthropic key，否则全站不可用 | 无 key = 降级为 Prompt 模式（规则引擎全功能），有 key = 加真出图 | 让"看得见的价值"不依赖付费条件 |
| 演示输入 | 手打文字 | 手打文字 **+ 书签脚本从亚马逊商品页一键抓** | 网页跨域读不到亚马逊 DOM；不给用户一个"能拿到真实数据"的通道，工具就只是个玩具 |

**一句话**：视觉创作那套规则、模板、Prompt 结构，与原版是同一份（数据同源、结构同构）；
外层编排从"AI 驱动"换成"规则驱动"，换来可验证性与零门槛。

## 二、核心功能模块（12 个）

### 模块 1 · 视觉创作编排（`assets/prompt-engine.js` + `orchestrator.js`）

输入一句话 → 六步确定性流水线 → 输出可直接用的 Prompt（或整套 14 张）。

```
① matchTemplate        **全自动**挑模板，不需要用户先手选
                      词证据：trigger_phrases > 别名层 > keywords，再比词长、再比位置
                      上下文：品类亲和 +6 ／ 驱动亲和 +3 ／ 有参考图 +3
② diagnoseConversionDriver  视觉/痛点/情感价值 三选一 → 决定主图推进顺序
③ detectCategory       8 个品类 → 套用该模板的 category_tips（**也在第 ① 步之前算好，喂给匹配**）
④ buildStyleLock       10 维度 Style Lock，多图任务每张原样复用同一段
⑤ composePrompt        按 SKILL.md 的 9 段结构组装（见下）
⑥ auditPlan            机械自检，逐张核 9 条硬约束
```

**关于「模板自动匹配」的四问四答**（四项都写进了自检，改坏会红）：

| 问题 | 答案 |
|---|---|
| **什么时候触发** | 每一轮对话都跑一次（`runLocalTurn` 第 ① 步）。输入 = 当轮文本 **+** 同一轮已算出的上下文（品类／驱动力／有没有参考图）。**没有关闭开关**，只有"显式指定"能覆盖它。 |
| **按什么规则匹配** | 两段证据：**词证据**（上游 `trigger_phrases` + 本层别名层 + `keywords`）与**上下文证据**（品类／驱动／参考图）。排序时**词证据永远优先** —— 上下文只负责"打平时决胜"和"一个词都没命中时接管"。 |
| **优先级顺序** | 显式指定 → 词证据（trigger > 别名 > keyword，再比词长、再比出现位置）→ 上下文（品类 +6 > 驱动 +3 ＝ 参考图 +3）→ 按 `order` 兜底。🔴 词权重**只做同位决胜**：把它加进主排序键，会把「直播间场景图」判成 `lifestyle-scene`（这是真踩过的坑，有回归断言守着）。 |
| **匹配不到怎么办** | 交给上下文**按品类回落**（`fashion→ghost-mannequin`、`electronics→device-mockup`、`pet→lifestyle-scene`…）；**连上下文都没有**（纯乱码）才落 `01-hero-image`，并在"依据"里**如实写这是兜底**，不假装匹配上了。 |

> 为什么要加"别名层"：25 个模板 JSON 来自参考仓（别人的仓库，MIT），`build-templates.mjs` 的铁律是**只消费不改写**。
> 但实测发现那套词表里 **`T恤` / `衣服` / `tee` / `shirt` / `apparel` 全部 0 命中**，服装类需求全被丢给白底主图。
> 所以补在读法层（`TEMPLATE_ALIASES`）——**上游文件一个字节都没动**。
>
> 模板库里还有个**「自动匹配预览」**：敲一句话，实时显示会选到哪个、依据是什么、还有哪些备选——自动匹配要**可审议**，不能是黑盒。
> 「固定用这个模板」按钮**只作用于下一条消息**，顶栏会出现提示且一键可撤销（做成粘性状态的话，用户点过一次就会在之后所有对话里静默违背自动匹配）。

`composePrompt` 的 9 段结构（**对齐 SKILL.md 原文顺序**）：

1. Campaign Style Lock（多图任务第一段，逐字相同）
2. 主体和场景（详情页以 `E-commerce infographic layout —` 起头）
3. 目的与情绪
4. 构图 / 镜头 / 取景（**显式写出角度关键词**）
5. 光线、颜色、材质纹理
6. 风格与真实感等级
7. **平台限制与画幅**（画幅比例 + 产品占比数字 + 留白下限）
8. **图片内文字**（三层信息架构：核心承诺 ≤15 字 / 证据 2-3 个 / CTA ≤8 字）
9. 否定清单 + Anti-AI 处理

### 模块 2 · 六条铁律的代码化

| 铁律 | 落地方式 | 可验证点 |
|---|---|---|
| 1 颜色用 hex 不用形容词 | `hexify()` 把中英文颜色词映射到 hex 表（**42 个色值**；单字色词强制带「色/调/底」后缀，避免误伤"金属""粉末""网红"；**英文一律走词边界**，否则 `hundred` 会被 `/red/i` 命中成 `hun#C0392B`） | 断言 `#[0-9A-F]{6}` 必须出现；反向断言 `hundred/blueprint/wooden` 不被改 |
| 2 产品占比数字化 | `FIGURE_SPEC` **八种图型**各带占比区间（卖点副图 25-30%、场景图 20-25%、信息流 40%、搜索广告 45%、SKU 卡 60-70%、详情页 30-40%、设计主图 35-40%、**亚马逊合规首图 85-100%**） | 断言 `product occupies 35-40%`；首图另有独立断言 |
| 3 留白显式声明 | 同上，各图型带留白下限（≥45% / ≥50% / 30%）；**首图是上限 ≤15%**（不是下限） | 断言 `at least 45%`；首图断言 `at most 15%` |
| 4 否定清单不能省 | `negativeConstraints()` 基础 7 项 + 按场景追加；**首图另有 9 项专属禁止**（文字/logo/边框/道具/多件/阴影/渐变底） | 断言 `Do NOT add:` |
| 5 平台预留空间 | `platformReserve(platform)` 两套返回：**国内电商**＝"顶部中央 200×100 留给价格浮层 + 左上角 200×100 留给 logo"；**亚马逊首图**＝"整幅不留任何叠加、角标、边框与文字" | 开关 `includePlatformReserve`；首图 Prompt 里出现的是"整幅不留"那句 |
| 6 三层信息架构 | `infoArchitecture()` 三层各自带字数上限并**返回 problems**；⚠️ **首图例外**：平台法规优先，首图写 `In-image text: NONE` | 三层各越界一次 → 报 3 条；首图断言不含 `28-48pt` |

> 🔴 **铁律 2/3/6 在首图上必须让位给平台法规。** 这不是"多写一句注意"，
> 而是两套**互相矛盾**的口径：设计稿说"产品占 35-40% + 留白 45%"，亚马逊首图要求
> "产品占 85-100% + 纯白底 + 零留白（≤15% 空）"。把两者相加是 130%，算术上就不成立。
> 所以代码里把「图位（slot）」和「构图占比」**分成两层建模**，首图走 `AMAZON_MAIN_IMAGE`
> 法规层，其余图走 `FIGURE_SPEC` 设计层，并在自检里用 4 个反向测试锁住首图那几条硬约束。


### 模块 3 · 多角度镜头规则（可机械验证）

6 种角度（正面 3/4、平铺俯拍、侧面 90°、背侧 45°、低角度仰视、高角度俯视）
× 5 种景别（全景、中景、特写、微距、局部）。

`assignAngles(count, {kind})` 做**确定性轮转**（不随机，所以可复现），并返回审计结果：

- 主图序列 ≥3 种角度，其中 ≥1 张特写/微距
- 详情页 ≥4 种，其中 ≥2 张特写/微距
- 不能连续 3 张同角度
- 全景占比 ≤40%，仰视和俯视各 ≥1 张

### 模块 4 · 跨境 Listing 文案与合规质检（`assets/listing.js`）

**28 条规则**（14 条硬规则 P + 14 条软规则 C），每条都带 `why`（为什么定这条）和 `source`：

| 规则来源 | 条数 |
|---|---|
| 平台公开规则（含《Misleading and prohibited claims》202024200、卖家行为准则、**2026-07-27 标题新规**） | 17 |
| 行业通行做法 | 5 |
| 行业通行做法（第三方合规清单，**明确标注非官方明文**） | 1 |
| 项目自定义（显式标注，不当官方标准） | 5 |

### 🔴 2026-07-27 标题新规：本项目改动最大的一处口径更新

亚马逊把标题从 200 字符砍到 **75 字符**，腾出的额度改由新字段 **Item Highlights**（125 字符，
后台显示名 Item Highlights / API 属性名 `title_differentiation`）承载，两者构成「两段式标题」。
口径来源以 **SP-API 官方开发者文档**《Submit modular titles》为准（字段名与上限是白纸黑字），
并与 Seller Central《Product title requirements》FAQ、欧洲站公告三方交叉印证。

| 字段 | 上限 | 计法 | 关键性质 |
|---|---|---|---|
| Title（`item_name`） | **75** 字符 | 字符（含空格） | media（图书/音乐/影像）是**唯一例外**，仍为 200 |
| Item Highlights（`title_differentiation`） | **125** 字符 | 字符 | **参与搜索**，显示在搜索结果与详情页标题下方 |
| 两段合计 | **200** 字符 | 字符 | 官方原文：两项共享这 200 字符额度 |
| （项目自定义）标题建议上限 | 70 | 字符 | 留 5 字符余量，**不是**平台规则 |

本次随之落地的 8 条新规则：

| 规则 | 档 | 判什么 |
|---|---|---|
| `P1`（改） | P | 标题超 75（media 走 200），且 detail 里写清**超限的真实后果** |
| `P4`（改） | P | 标题 71–75：已逼近硬顶，media 口径下跳过 |
| `P13` | P | Item Highlights 超 125 |
| `P14` | P | Item Highlights 含促销词/最高级/特殊符号（与标题同口径） |
| `P15` | P | 站外引流与联系方式：网址 / 邮箱 / `contact us` / 加微信 |
| `C10` | C | Item Highlights 为空（放弃 125 字符可搜索额度） |
| `C11` | C | Item Highlights 与标题高度重复（官方：两段要各说各的） |
| `C12` | C | 疑似电话 / 站外社交平台名（**软规则**，理由见下） |
| `C13` | C | 标题重复词（75 字符时代它直接吃额度） |
| `C14` | C | 标题主观修饰词（Premium / High Quality…，词表是项目自定） |

> 🔴 **三条刻意写准、避免误导的地方**
>
> 1. **超限不等于"被拒收"**。官方原文是超 75（最多 200）**仍可提交并被接受**，Amazon 会按 AI 建议
>    **自动拆分改写**你的标题（品牌方另有 14 天复核期）。真实代价是**失去标题控制权**，
>    以及**连带丢掉 Item Highlights 的提交资格** —— 官方明文：只有 `item_name` ≤75 才能提交
>    `title_differentiation`。把后果写成"被拒收"是造谣，会让人做错决策（`P1` 的 `why` 里有断言锁住）。
> 2. **电话只做软规则**。`350-500-1000` 这种三段规格串数字量就有 10 位，电话硬禁必误报；
>    而误报会让卖家不再相信整个质检结果。所以只报"形态更像电话"的，并标"请人工确认"。
> 3. **`C14` 的词表是项目自定**。官方只给了原则（Subjective commentary）和两个例子
>    （HOT ITEM / BEST SELLER），**没给词表** —— 所以定 C 级并在 `source` 里写明。

**规则的分档不是"重要程度"，而是"错了会不会被打"：**

| 档 | 含义 | 例子 |
|---|---|---|
| **P 硬规则** | 平台级，直接对应下架/压制/拒收 | 标题超限、促销词、特殊符号、疾病声明、农药抗菌声明、HTML 标记 |
| **C 软规则** | 转化 / 可读性 / 需举证，不影响合规 | 核心词前置、利益词、符号密度、环境声明、五点引导词结构 |

> 🔴 **2026-09-28 把「五点必须大写引导词开头」从 P 降到了 C。**
> 它是**行业惯例**，没有任何平台文档要求。放在硬规则会让"五点全过、只是格式不合惯例"
> 的 listing 被报成"发布前必须修改"——结论强度与真实风险不匹配，这是质检工具最常见的失信方式。

另外：

- `mineKeywords()` 1/2/3-gram 词频挖掘（**不调 LLM** —— 词频是可复现的客观量，交给模型反而不可验证）
  - ⚠️ 返回值里带 `disclaimer.isSearchVolume = false`：这是**词频**，不是搜索量/竞争度/转化率，界面上会显式提示
- `buildSearchTerms()` 按**字节**而非字符卡 250 上限
- `generateListingDraft()` 规则式草稿 + A+ 内容 7 屏骨架 + 商品描述
  - 🔴 新规下标题溢出**不再丢弃**：被剥下来的规格/人群片段、以及卖点里的材质句
    **搬进 Item Highlights**（这正是官方 Before/After 示例的做法）；
    长卖点句**刻意不搬** —— 它们本来就要进五点，搬过去只是重复。
  - 字段分配按 `role` 决定（`spec`/`audience`/`material` → Highlights，`feature` → 五点）
- **词边界匹配**：`matchWords()` 用正则而非 `includes`，避免 `secure` 命中 `cure`、`freedom` 命中 `free`
- **品类差异化**：复用 `detectCategory()` 的同一套词表，8 个品类各带 `CATEGORY_CLAIMS`
  （`antibacterial` 写在厨房清洁剂上是必需注册声明，写在袜子上就是违规抗菌宣传）
- `exportListingFields()` 导出**按亚马逊后台字段**的可粘贴文案（后台是一个字段一个框，整段 JSON 填不进去）；
  三种计法分开：**标题 / Item Highlights / 五点 / 描述按字符，Search Terms 按字节**；
  另带一份 `budget` **两段式总账**（标题 + Highlights 合计占 200 的多少、
  以及标题超限时"Highlights 提交不上去"的显式提示）
- `exportFlatFileCsv()` 导出 **Flat File 风格 CSV**：列名用官方属性名、按 RFC 4180 转义
  （五点带逗号是常态，不转义会直接把一行撑成多列）。
  ⚠️ 界面上明确写了它**不是**可直接提交的官方模板 —— 各类目模板列名不同，
  把对照文件说成模板，用户传上去才报错，比不做这个功能更糟
- **类目口径是显式开关**（普通 ≤75 / media ≤200），不让程序猜品类：
  这条判错会让一个超限标题被报成"通过"

质检结果分四态：`命中` / `通过` / `跳过`（字段为空）/ —— **空字段算跳过，不算通过**。

#### 合规词表：口径、覆盖，以及**刻意不收录**的词

疾病/抗菌/农药声明那几张表逐条抄自亚马逊官方页面（Seller Central `202024200`），
不是"凭印象列的常见违规词"。官方疾病表有 80+ 条，本项目**剔掉了 7 条**：

| 剔除的词 | 为什么剔 | 保留的等价写法 |
|---|---|---|
| `add` | 会命中 "**Add** to cart"、"Add-on" | `attention deficit`、`adhd` |
| `sad` | 会命中所有 "**Sad** puppy" 类玩具/绘本 | `seasonal affective disorder` |
| `mono` | 会命中音频设备的 "**mono** output" | `mononucleosis` |
| `pid` | 会命中温控器的 "**PID** controller" | `pelvic inflammatory disease` |
| `crabs` | 会命中海鲜与螃蟹玩具 | `pubic lice` |
| `tbi` / `ngu` | 纯缩写、日常无语义、收益为零 | `traumatic brain injury` / 全称 |

同理，**没有**收 `perfect`（`perfect for gifting` 是海量合规 listing 的写法）、
**没有**把 `%` `#` `+` 放进符号黑名单（`100% Cotton` / `Model #A` / `2+1 Pack` 都合法），
改成 `C7 符号密度` 规则兜底。

理由很直接：**质检工具的误报会直接消耗信任，一次误报换来的是一次忽略。**
宁可少抓一条，也不能让用户学会"它老是瞎报，别管它"。

表里剩下的歧义词（`stroke` 有"笔触"义、`gout` 罕见）在规则文案里写的是
「**疑似**……命中后需人工确认」，不写「确定违规」。

#### 关键词覆盖度分析（`analyzeCoverage`）—— 2026-09-29 补的

对应同类方案（`nexscope-ai/Amazon-Skills`）里的"关键词覆盖追踪"，按本项目的方式重做：
**纯函数、零网络、可断言**。逐词检查它落在 **标题／五点／描述／后台词** 哪几处，并**刻意分成两类**：

| 类别 | 含义 | 在界面上的角色 |
|---|---|---|
| `gaps` | **你选定的**候选词里，竞品在打、我完全没有 | 🔴 **待办** —— 优先补进标题或五点 |
| `minedGaps` | 从竞品语料挖出的其他词 | ⚪ **线索** —— 含 n-gram 噪声（如 `dogs reduces`），明确写「只当线索看」 |

为什么要分开：**混在一起，真缺口会被噪声淹掉**（实测把 40 个挖出的词混进去后，
用户真正该补的 `anti-pull` / `small dogs` 直接看不见了）。

配套的三个尺度：
- 字段权重 **3/2/1/1**（标题/五点/描述/后台词）—— 标注为**行业通行做法，不是官方明文**
- 竞品语料**按句拆分**后再挖 n-gram（否则会产出跨句假短语）
- 没给竞品语料时 `competitor` 是 `null` 而**不是 `false`** —— 不能用"假"冒充"竞品没覆盖"
- 界面与 `note` 都写明：**这是文本覆盖，不是搜索排名、不是搜索量**

### 模块 6 · 图片库与打包下载（`server.mjs` + `assets/zip.js`）

生成的图落在 `data/gen/`，前端「图片库」视图把它们排成缩略图墙：单张下载、单张删除、
以及**一键打包成 ZIP**（服务端 `GET /api/library?zip=1`）。

打包器是**自己写的**（`assets/zip.js`，176 行）—— `archiver` / `jszip` 会带进几十个依赖，
违背"零 npm 依赖"这条硬约束。ZIP 的存储模式（method=0）本身就只是一串定长头 + 原始数据，
CRC32 用 Node ≥20.15 内置的 `zlib.crc32` 就够：

- **不压缩**：图都是 PNG/JPEG，本身就是压缩格式，再套一层 deflate 收益接近 0
- **必须置通用位标记 bit 11**（UTF-8 文件名），否则中文名在 Windows 资源管理器里全是乱码
- **三处偏移必须互相吻合**（本地头 / 中央目录 / EOCD），错一个解压器就报"文件损坏"
- **ZIP64 越界要响亮报错**，不能让 4 字节字段静默回绕后产出一个打不开的包

> 已用 Python 的 `zipfile.testzip()` 做过**真解压验证**（含中文文件名与空包）。

### 模块 7 · 本地产物（`assets/store.js`）

采集结果 / 图像方案 / Listing 草稿 / 覆盖度报告会自动留档，刷新不丢。

**用 IndexedDB 而不是 localStorage**，原因不是"新一点"：

| | localStorage | IndexedDB |
|---|---|---|
| 容量 | ~5MB | 数百 MB |
| API | **同步**（几百 KB 会卡住 UI 线程） | 异步 |

本项目要存的是**整页搜索结果的 JSON + 14 张图的 Prompt 全文** —— localStorage 既装不下、也会卡。

**一个刻意的设计**：**产物（可导出/可分享）与配置（密钥，绝不导出）分两层存。**
`store.js` 只碰产物；API Key 仍走服务端 `.env.local`。这样"把产物导出发给同事"
这条路径**从数据结构上就不可能夹带密钥**，不靠代码自觉。

「本地产物」视图里可以按类查看 / 载入 / 单条导出 / 删除，也可以**整体导出成 JSON**、
或把别人给的 JSON **导回来**。写满配额时 `store.js` 会丢弃该类最旧一半再重试一次（只重试一次）。

> 也可测性优先：`store.js` 顶层不碰任何浏览器 API，`isAvailable()` 在没有 `indexedDB` 的环境
> **返回 `false` 而不抛错**；记录构造/裁剪/排序/指纹/摘要全是**导出的纯函数**，
> 所以能在 Node 里断言一遍、再在真浏览器里断言一遍。

### 模块 8 · Rufus / Alexa 信息架构检查（`assets/rufus*.js`）

已有一套 28 条质检在查"**这句话会不会被平台罚**"；这一块查的是"**机器能不能把你的商品读进去**"。
AI 购物助手（Rufus / Alexa for Shopping）只引用**结构化字段**和**能检索到的句子** ——
字段空着、事实自相矛盾、单位打架、图上的字没写进文案，这四种情况下信息对机器等于不存在。

| 组 | 查什么 | 依据档位 |
|---|---|---|
| **R1** attributes 完整性 | 8 个类目的属性表里，官方明文的必填字段 / 推荐字段有没有空着 | 官方帮助文档正文 / schema |
| **R2** 跨字段事实一致性 | 材质互斥（`cotton` vs `polyester`）、件数矛盾（标题 2 件、五点 3 件） | 行业通行 |
| **R3** 单位制一致性 | 同一维度组内英制与公制并存（标签 `32 fl oz`、描述 `1 liter`） | 行业通行 |
| **R4** 买家问题覆盖矩阵 | 8 类目 × 10 个买家高频问题，文案里有没有答案线索 | 行业通行（无官方问题清单） |
| **R5** 图内文字未文本化 | 贴在图上的规格文字有没有同时写进文本字段（用户手贴 `imageText`，**不做 OCR**） | 项目自定义 |

三条纪律：

1. **数据与逻辑分离** —— `rufus-data.js` 是纯数据（不 import 任何模块），`rufus.js` **不写死任何属性 key**。
2. **出处分两档，未知必须抛异常** —— `source` 只有 `amazon-guide` / `amazon-schema` / `practitioner` 三个合法值，
   `tierOf()` 是唯一映射点；**传进未知值直接抛错，绝不静默归为 official**。**宁可标低不许标高。**
3. **分级保守** —— 只有 R1 的必填档 + 官方帮助文档正文才判 P（"发布前必须修改"）；
   跨字段 / 单位制 / 图内文字都是从业者口径，**报硬规则就是撒谎**。

> 🔴 **两条已知边界写在代码里，不是藏着**（设计取舍见《功能细节》§20.5 与 SPEC §8）：
> ① R2 的 guard 是**字段级二值** → `title "Leather Belt"` + `description "Faux Leather Strap"` **会漏报**；
> ② R2 的否定窗口固定 **2 词** → `"This is not the real genuine leather"` + `"synthetic"` **会误报**。
> 两条方向相反、**分开写**，并且都带双向锁断言（防后人"顺手修坏另一侧"）。
> **不把它们修掉的理由**：收窄 ① 会让 `"Wool Coat"` + `"Acrylic lining"`（完全合法）变误报；
> 放长 ② 会让 `"not only cotton but also polyester"` 被静默压掉 —— **误报比漏报贵，但系统性漏报比误报更坏。**

界面上一张卡（挂在「文案与质检」视图内，**不新增导航视图**），三条"界面不许说假话"的硬要求：
跳过项必须带原因可见；结论文案只读引擎的 `summary.conclusion`（不另写一套）；只有 P 级命中才染红。

### 模块 9 · 竞品榜单实时抓取 → 关键词权重 → 文案提示词（`bestsellers.js` + `competitor-keywords.js` + `copy-prompts.js`）

2026-10-02 从另一个独立工具（「亚马逊竞品销量榜工具」）整合进来的一条链。
勘察时发现的关键事实：本工作台**早就有竞品关键词链**（`#lCorpus` 竞品语料 → 词频 → 一键填 `#lKeywords` → 多竞品共识），
**缺的只是最后一跳** —— 把算好的结论拼成一段可复制的**文案**提示词（`prompt-engine.js` 只做**图像**提示词）。
所以这次是"补上缺的那一半"，不是"搬一整个工具进来"。

三段职责分得很清：

| 段 | 模块 | 联网吗 | 干什么 |
|---|---|---|---|
| **抓** | `assets/bestsellers.js` | ✅ **全项目唯一主动爬第三方站点的通道** | 抓亚马逊 Best Sellers **公开榜单页** → 名次 / ASIN / 标题 / 星级 / 评论数 / 价格；带 10 分钟缓存 |
| **算** | `assets/competitor-keywords.js` | ❌ 纯本地 | 1–3 gram 切词 + 权重模型（覆盖率×50% + 位置×30% + 精准度×20%），只留出现 ≥2 次的词 |
| **写** | `assets/copy-prompts.js` | ❌ 纯本地 | 拼 5 类文案提示词（拆解 / 标题+亮点 / 五点 / 后台词 / 本地化），字符上限**全部**取自 `listing.js` |

三条出网纪律（**都是相对原工具有意加严的，不是照抄**）：

1. **主机硬白名单** —— 只允许 8 个 amazon 域，且路径必须是 `/gp/bestsellers/` 或 `/zgbs/`；不在名单里直接 400，不拼进请求。
2. **过 `assertPublicUrl`** —— 复用 SSRF 那套判据（DNS 解析后判内网），**重定向之后再判一遍**（`Location` 是第二个注入点）。
3. **服务端 `?href=` 参数自己过白名单** —— 否则这个参数就是一条任意 URL 抓取通道。
   安全回归里有 13 类非法参数 × 2 条路由的断言，全部要求"**在发出网络请求之前**就 400"。

> 🔴 **界面不许说假话**：抓不到就说抓不到（显示失败原文），**绝不摆假数据**。
> 亚马逊改页面结构时会表现成「抓到 0 条」并**抛错**，不是静默。
> 也不要把它说成"销量榜" —— 亚马逊**不公开销量**，评论数只是**从业者口径**的代理指标，界面与提示词里都按这个措辞写。
>
> 另一处实测修掉的缺陷：请求头不带 `Cookie: i18n-prefs=USD; lc-main=en_US` 时，亚马逊按**请求方 IP 所在国**返回本地化结果
> —— 本机在中国，整列价格会变成 `CNY 60.39`。原工具的 Python 侧强制了 USD，Node 侧漏了。浏览器自检里有断言锁死"价格必须以 `$` 开头"。

界面上一张卡（第 ⑦ 卡，挂在「文案与质检」视图内、⑥ Rufus 卡之后，**不新增导航视图**）。
**刻意不搬**原工具的两块：它的整套前端页（1113 行，与这里的 8 视图外壳重复）、
以及它的 `/s?k=` 关键词搜索路径（会给零依赖项目引入 Python 运行时，且原代码注释自述该路径已被亚马逊 503 封锁）。

八个工具，全部是现有函数的薄封装（不写第二份实现）：

| 工具 | 底层 | 干什么 |

|---|---|---|
| **词根** | 人（`assets/keyword-seeds.js`） | 14 组 / **194 条**人工挑过的英文词根。词根是判断，不是数据 |
| **长尾** | 机器（搜索建议接口） | 每个词根取 ~10 条**真实买家搜索词**，零 Key、零费用。194 词根 → **2,135 条**去重词面（含二轮扩词） |
| **ASIN** | 机器（Best Sellers 公开榜单） | 13 个类目 × 2 页 → **769 条** ASIN（标题 / 星级 / 评论数 / 榜单名次齐全，详情页链接按 ASIN 派生；**价格只有约 1/3 条目有值** —— 榜单卡片本身常不显示价格） |

跑法：GitHub Actions 每周一 02:17 UTC（+ 手动触发）跑一次，把快照提交进仓库：

```bash
node tools/collect-keywords.mjs --site com --pages 2 --delay 1100 --deep 30 --max-requests 260   # 约 7 分钟
```

产物两份：

- `data/keywords/latest.json` —— 完整快照（词面 + ASIN + 各数据源状态），约 850 KB；
- `data/keywords/history/YYYY-MM-DD.json` —— 只留摘要（数量 / 新增 / 消失 / 分类目 + **词级投影 `topTerms` 前 800 条、`asinRanks` 每类前 30**），最多 **104 份**（≈两年）。投影只干一件事：判断一个词是**首次**还是**回归** —— 没有它就只能记 `unknown`，不猜；
- `data/keywords/_status.json` —— **最后一次尝试**的结果（`latest.json` 只反映最后一次成功）。定时任务跑挂了，快照还看着正常，唯一证据在这里：`ok:false` + `reason` + `exitCode`，并保留上一次的 `lastSuccessAt`（否则「烂了多久」永远算不出来）；
- `data/keywords/logs/YYYY-MM-DD.log` —— 每次运行的完整输出。从计划任务跑的时候 stdout 没人接收，不留日志等于跑挂了没证据。

六条纪律：

1. **失败不覆盖** —— 一条都没抓到时**拒绝写盘**并以 exit 2 收场。用空数据盖掉好数据是这类采集器最常见的自毁方式，而且没人会发现。
2. **有节流、不并发** —— 每请求间隔 1.2s，194 个词根 + 二轮扩词约 7 分钟。高频轮询唯一确定的结果是被风控，然后连"这周有没有变"都不知道了。
3. **预算不够要说出来** —— 预算**推导**而来（`词根数 + min(deep, 词根数)`），不再是一个会过期的魔法数；手给 `--max-requests` 时 `budgetSource` 会记成 `cli`。有人把它调到 80 时，剩下的词根会被跳过，报告与 `sources.suggest.skipped` 都会写明；`sources.suggest` 里还有 8 个自证字段（`rootsRun` / `deepAttempted` / `deepSkippedDuplicate` …），可以手算核对「实发 = 词根 + 深挖」。
4. **`firstSeen` 只在一个地方算** —— `keyword-vault.js` 的 `buildSnapshot()`，采集器 / 接口 / MCP / 界面都调它。两边各算一遍的后果是"这词什么时候第一次出现"永远对不上。
5. **陈旧要说出来 —— 而且分四档** —— `fresh` ≤10 天 / `stale` 11–21 天 / `dead` >21 天 / `missing`（没快照）。接口与 MCP 返回 `state + ageDays + note`，界面按四态染色并给出下一步动作（stale：「别当本周数据用」；dead：「先去修定时任务」）。两档不够用：
   "有点旧"和"烂了三周"需要的动作完全不同，而界面只说"已过期"等于什么都没说。
6. **「消失」里有噪声** —— 连跑三次的实测：第 1→2 轮有 211 条没再出现、同时多出 549 条；第 2→3 轮完全一致（新增 0 / 消失 0）。词面会漂，但不是每次都漂。所以 `newKeywords` / `droppedKeywords` 只能当"这周词面变了"的粗信号，**不能读成"这个词没人搜了"**。

消费方三处，读的是同一个文件：

- 界面「② 关键词挖掘」里的**载入本周词库**按钮 → **体检卡**（新鲜度四态 / 站点是否已验证 / 价格·评分字段完整度 / 数据源状态 / 上次采集成败与耗时），再给 roots / new / az 三个排序切换，最后才是「把前 30 个词填入关键词框」；
- `GET /api/keywords?q=&limit=&category=&sort=`；
- MCP 的 `keyword_snapshot` 工具。

接口约定（2026-11-07 补齐）：

- `?category=kitchen` **同时**筛关键词（按 `groups`）与 ASIN（按 `group`/`category`）—— 以前文档写了、代码没做，参数被静默忽略；
- 返回里带 `keywordsTotal` / `keywordsTruncated` / `asinsTotal`：单次最多给 500 条词、500 条 ASIN，**截断必须能看见**（以前是静默夹在 500，调用方会以为词库只有 500 条）；
- `latest.json` 按 `mtime + size` 缓存解析结果：文件没变不重读，变了必须重读 —— 陈旧判定不进缓存（它依赖"现在几点"）；
- 返回里还有一个 **`trust`** 对象（新鲜度 / 采集状态 / 站点已验证 / 截断 / 字段覆盖率 / 空词根数 / 数据源状态 / 预算 / 首次回归分不分得出）。**界面照它渲染，不自己再算一遍** —— 两处各算一份，迟早会打架（一边 33% 一边 50%）。

> 🔴 **它仍然不是"搜索量"**。建议词只说明「有人这么打字」，不说明有多少人搜；ASIN 的 `rank` 是榜单名次，不是销量。
> 亚马逊不公开绝对搜索量 —— 本项目**自己不产、也不估**任何搜索量数字。唯一会出现搜索量的地方是你从卖家精灵 / Helium 10 / JS 导入的 CSV，界面会标明「来自哪个文件」，并且那一列只用于排序取舍，**不参与覆盖判定**。

### 4.2 关键设计：为什么用确定性编排替代 Claude Agent SDK

原版靠 SDK 让模型自己决定「要不要调 get_template」「生成什么 Prompt」。这带来四个问题：
模板调用不可控、结果不可复现、没 key 跑不起来、约束靠模型自觉。

本项目把编排写成**纯函数流水线**，好处是能直接写断言（见第六节）：

```js
const plan = planImagePack({ subject: "pet automatic feeder", driver: "pain", styleLock, pack: "pdp" });
auditPlan(plan);  // → [] 表示 14 张全部通过 9 条硬约束
```

这条断言在浏览器、服务端、CI 里跑的结果完全一样。

### 4.3 单一事实源（这条踩过坑）

| 数据 | 唯一事实源 | 派生方式 |
|---|---|---|
| 25 个模板 | 参考仓 `references/templates/*.json` | `npm run build:templates` 生成 `assets/templates.js`，**不手抄** |
| 编排逻辑 | `assets/orchestrator.js` | 服务端 `server.mjs` **import 复用**，不重写 |

> ⚠️ 开发中真栽过一次：服务端曾有**第二份**主体抽取实现，
> 结果离线路径修好了、服务端还在跑旧逻辑（浏览器里看到的仍是脏主体）。
> 现在自检里有一条**源码级断言**专门盯着这件事：
> `server.mjs` 必须出现 `runLocalTurn`，且不得再出现手写的主体抽取与简报 Markdown。

### 4.4 容错取舍

「算不出来宁可给占位符，不给假数字」：

- 主体抽不出来（用户只说了风格）→ 不硬凑，填 `{PRODUCT}` 占位符，**并在简报首行显式告警**
- 质检字段为空 → 状态是 `跳过`，**不记作通过**
- 没配图片 key → 明确报错说"Prompt 可用但出不了图"，不静默失败

## 五之二、安全性：六个"看起来没事、其实能被读走/打穿"的点

这一节是从外部审阅意见里**核验后采纳**的部分，加上核验过程中**自己发现**的两处。
每一条都配了端到端回归（`npm run test:server`，真起服务真发请求）。

| # | 问题 | 原来的样子 | 现在 |
|---|---|---|---|
| 1 | **静态服务目录穿越** | `serveStatic` 只挡了 `..` 逃逸，项目根下的**普通文件全可读**：`GET /.env.local` 直接拿走出图 API Key，`GET /server.mjs`、`GET /data/gen/*` 同理 | 改成**白名单**：只放行 `index.html` 与 `assets/`，其余一律 404（不报 403 —— 不告诉探测方"这里有个东西"）。回归里 15 条路径全部 404 |
| 2 | **Host 头不校验（DNS rebinding）** | 只监听 127.0.0.1 就以为安全了。但攻击者把自己的域名解析到 127.0.0.1，受害者浏览器就会把请求发到本机服务，而 `Host` 是攻击者的域名 | 加 Host 白名单（只认 `127.0.0.1` / `localhost` / `::1`）。⚠️ 测这条**不能用 `fetch`** —— Node 的 undici 把 `Host` 当禁止修改的头静默丢弃，用 fetch 测永远是 200，那是测试假象（踩过，见 `verify-server.mjs` 注释）。**2026-11-05 补**：绑 `0.0.0.0` 且没配 `PUBLIC_HOSTS` 时原来返回 `null` = 整体跳过校验（fail-open），现在永远返回集合（fail-closed，最坏结果是被 403），启动日志会打印实际放行名单 |
| 3 | **SSRF** | 生图接口的响应里带 `url`，服务端会去下载它；这个 url 完全由**上游服务**决定。上游被投毒 → 本机以自己身份访问 `169.254.169.254`（云元数据）/ `127.0.0.1:xxxx`（本机其它服务） | `assertPublicUrl()`：只允许 http/https → DNS **解析**出全部 IP → 逐个判内网段 → 再 fetch，且 `redirect: "manual"` 禁自动跳转（3xx 是绕过第一次校验的常见手法） |
| 4 | **`/api/config` 非原子写** | 直接 `writeFileSync('.env.local')`。写到一半崩溃/断电会留下**半截配置**，密钥与 URL 一起丢 | 先写 `.env.local.tmp` 再 `renameSync` 原子替换；同时给 `imageBaseUrl` 加 `http(s)://` 格式校验（它之后会被拼进 URL 再出网） |
| 5 | **前端 id 拼错会静默失效** | 手工维护 DOM 与 `$("#id")`，拼错没有任何提示，表现为"按钮点了没反应" | 自检里加源码级断言：页面上每个 `<button id>` 都必须在 `app.js` 里被绑定；`app.js` 引用的每个 `#id` 必须真实存在（静态页面或自己渲染的模板里） |
| 6 | **竞品抓取接口会变成「任意 URL 抓取通道」** | 整合进来的抓取接口收一个 `?href=` 参数（用于子类目链接）。不校验的话，它就是一条"让本机服务去访问任意地址"的通道 —— 打 `169.254.169.254` 拿云元数据、打 `127.0.0.1:xxxx` 探本机其它服务 | 参数三层校验：站点代码 / 类目 slug 必须在清单内；`href` 必须过「8 站主机 + https + 路径形状」白名单（`amazon.com.evil.com` 这种后缀骗局也挡）；最终地址再走 `assertPublicUrl` 判内网。回归里 **13 类非法参数 × 2 条路由**全部要求「在发出网络请求之前就 400」 |
| 7 | **`/api/config` 可被跨站写入（CSRF）** | 只解析 body，不看 `Content-Type` 也不看来源。任意网页可以用 `mode:"no-cors"` + `Content-Type: text/plain` 发**简单请求**（不触发预检），把 `imageBaseUrl` 改成攻击者域名 —— 下次生图，密钥就发到对方服务器 | 三道闸：① `Content-Type` 必须是 `application/json`（否则 **415**；跨站就得先过预检，而本服务从不回 CORS 头 → 预检必失败）；② `Origin` 必须与 `Host` 同源、`Sec-Fetch-Site` 只认 `same-origin`/`none`（否则 **403**，`Origin: null` 也拒）；③ 键名白名单，未识别的键进 `ignored` 回执 |
| 8 | **一次保存会删掉其他配置** | 用内存里的 `runtimeConfig` **重建整个** `.env.local`：只提交 `{imageModel}` → `CHAT_*` / `VISION_MODEL` / `COMPETITOR_SCRAPE` 全被删；提交 `{}` → 文件只剩一行注释；空值被 `continue` 跳过 → 密钥**永远删不掉** | 读现状 → 只合并本次提交的键 → 原子写回；`{}` 直接 **400** 且文件哈希不变；空值 = 删除该键；响应回执 `{written, removed, preserved, ignored}`，只回键名不回值 |

> ⚠️ **已知上限（写在这里而不是藏着）**：SSRF 这一层仍留有 DNS rebinding 的 TOCTOU 窗口
> —— 解析与 `fetch` 是两次独立查询。Node 内置 fetch（undici）不支持 pin IP，
> 要彻底堵住得换成带 `lookup` 钩子的 dispatcher。**本机 + 仅监听 127.0.0.1 的形态下可接受；
> 若要部署到公网，必须先补这一层。**

## 六、自检（这个项目的主张，必须能被机器证明）


## 八、诚实声明（已知限制）

1. **C 组软规则是行业通行做法，不是平台明文** —— 每条 `source` 已标注，别当官方标准用。
2. **`assets/templates.js` 是生成物**，改它没意义，要改去改参考仓的 JSON 再重新生成。
3. **书签脚本要用户手动拖**（浏览器限制），且依赖亚马逊 DOM 结构 —— 亚马逊改版就会失效，选择器需跟着更新。
4. **`auditPlan` 只能验证"Prompt 里写没写"，不能验证"图出来对不对"** —— 后者需要人眼或视觉模型，本项目没做。
5. **没有真实出单/转化数据**。所有数值（占比、留白、角度）都是**规则阈值**，不是从 A/B 实验里测出来的。
6. **`infoArchitecture` 的 15/3/8 字上限是项目自定义**（来自 SKILL.md 的口径），不是平台规则。
7. **生图成本**由用户自己的 API 账户承担，本工具不代付、不缓存结果超过本次会话。
8. **未在真实卖家工作流中试用过** —— 这是一次基于公开规则与开源 Skill 的复刻实现。
9. 🔴 **必须经 HTTP 访问，不能双击 `index.html`**（见 §七）。`file://` 下 ES 模块被 CORS 拦掉，**整个前端一行 JS 不跑**，而且 `file://` 下 IndexedDB 也不可用 —— 也就是说 `file://` 下"本地留档"与"图片库"**功能上不存在**。
10. **搜索页采集只解析当前渲染出的那一页** —— 不做自动翻页，也不处理排序/地区参数变更；要更多数据请翻页后再点一次书签。
11. **没有真实搜索量、没有竞品历史排名追踪** —— 本项目只做词频与文本覆盖，**刻意不接**付费关键词 API（见附四）。`disclaimer.isSearchVolume` 永远是 `false`。
12. **多竞品对比是"文本覆盖对比"，不是"排名反查"** —— 它回答"哪些词竞品都在打"，不回答"这个词有多少搜索量、排第几"。
13. **非英语站点只做到"词表与站点参数"** —— 日语/中文不做分词（CJK 占比高时会明确提示"词形不可直接填 Search Terms"），生图/生文案本身仍由模型完成。
14. **浏览器侧自检只证明"能跑通闭环"**，不证明布局好看、不证明像素级正确 —— 样式回归仍需人眼。
15. **Rufus 模块的判据大部分是行业口径** —— R2（跨字段事实）/ R3（单位制）/ R4（问题矩阵）/ R5（图内文字）**全部是 `practitioner`**，只有 R1 的必填档触到官方帮助文档正文。每条 `source` 都已标注，别当官方标准用；也正因如此，这一组几乎全判 C 级（"建议"而不是"必须改"）。
16. **R2 有两条方向相反的已知边界**（① 字段级二值 guard → 会漏报；② 否定窗口固定 2 词 → 会误报），两条都写成了断言并**刻意保留**，理由见《功能细节》§20.5 与 SPEC §8。**别"顺手修掉"其中一条** —— 那会把问题换到另一个方向，而且双向锁断言会红。
17. **R5 不做 OCR、不解析图像** —— `imageText` 必须由用户手贴；没贴就整体跳过。**「跳过」不等于「通过」**，界面上会显示跳过原因。
18. **R4 的覆盖判据用 OR，偏松** —— `answerHints` 里任一 key 命中即算"这条问题有答案"。我们能证明的只是"文案里有相关线索"，**不能证明"这句话真的回答了那个问题"**，所以专门有「通过（部分）」这一态。问题清单本身（8 类目 × 10 题）也是从业者经验值，**不存在官方问题清单**。
19. **R1 的 `required` 只是"能附上官方引用句"的字段**，不是亚马逊的完整必填清单（`brand` 就在 `recommended` 里）；且本项目**只检查"哪个字段空着"，不做生成式填值** —— 属性值有闭集约束（官方错误码 90057），填一个不在下拉里的值比空着更糟。
20. **竞品抓取依赖亚马逊公开榜单页的 DOM** —— 解析认 `data-asin` / `p13n-sc-price` / `out of 5 stars, N ratings` 三类选择器，亚马逊改版即抓不到（会**抛错**而不是静默给假数据）。另外：**榜单 ≠ 销量榜**，亚马逊不公开具体销量，评论数只是**从业者口径**的代理指标。
21. **关键词权重是启发式，不是搜索量** —— 覆盖率×50% + 位置×30% + 精准度×20%，衡量的是"这个词在这批竞品标题里的相对结构"，与搜索量、竞争度、转化率**都无关**。出现 <2 次的词会被直接丢弃，所以**会漏真长尾**；切词是英文正则 + 停用词表，**中文竞品标题不做分词**。
22. **文案提示词只是「给模型的输入」，不是产出** —— 它只拼文本、不调模型、也不校验模型输出。里面引用的字符口径与质检规则**同源**（都取自 `listing.js`，有反向锁），但**模型守不遵守不受本项目控制**。
23. **`/s?k=` 关键词搜索路径刻意不提供** —— 原工具走 Python `scrapling` 子进程，搬进来会给这个零依赖项目引入 Python 运行时依赖，且原代码注释自述该路径**已被亚马逊 503 封锁**。所以只有公开榜单页这一条通道，界面上写明，不假装"什么都能抓"。
24. **语种支持是不对称的** —— 停用词/词频有 7 套（en/de/fr/es/it/nl/ja），但**利益词表（C3）与 Prompt 输出只有 zh/en**。日/德/法等的五点会被标成「跳过·未判定」，不拿英文词表硬套。纯汉字日文标题仍会被判成中文（无法区分，写明的边界）。
25. **「主图禁 AI」与「AI 图打 XMP 标」是「待核实」** —— 前者是两条官方要求（主图须摄影作品、须如实代表商品）的**合并推论**，后者来自 IPTC/C2PA 规范；亚马逊是否强校验**没拿到官方原文**。所以它们出现在「交付前核对」里，不出现在「平台规定」里。
26. **`docs/测试盲区清单.md` 是这份 README 的配套** —— 1522 条断言全绿只说明"这些具体行为没坏"，**不说明规则符合平台规则**、也不说明在别人的网络/浏览器/数据下成立。哪些没测、哪些刻意不测，都在那份清单里。
27. **MCP 里没有"数据源"，只有"判断"和"一份本地快照"** —— 本 server 自身仍然不提供搜索量、ABA 排行（那需要账号级 Token，无法随代码分发）。**但工作台界面里可以自己接**：填自己的第三方密钥后，数据会作为「外部词表」出现在本周词库页，并和本地词库做交集；那份数据落在 `data/external/`（不进分享包），MCP 的八个工具不会因此多出数据源。唯一的 `keyword_snapshot` 读的是本仓库 `data/keywords/latest.json`，所以**只有拿到这份快照的机器上才查得到**；没有快照时它返回 `ok:false` 并说明怎么生成，不报工具错误。
28. **`amazon_suggest` 返回的是"建议词"，不是"搜索量"** —— 只说明"有人这么打字"，不说明有多少人搜。另外除 US、DE 外的站点参数**没有实测过**（`verifiedMarket: false`），返回空时工具会明说"分不清是没词还是参数没对上"，别当成"没人搜"。
29. **MCP 的判断与界面里的判断是同一份代码，不是两套** —— 八个工具全是现有函数的薄封装。所以界面上的已知边界（例如 C3 只认中英、覆盖度不是排名）在 MCP 里**一模一样**，不会因为换了个入口就变准。
30. **`mcp/server.mjs` 只做 stdio，不要挂到公网 HTTP 上** —— stdio 是本地子进程模型，天然没有暴露面；换成 TCP/HTTP 给外部用需要另加一层鉴权，本项目没做，也不建议直接照搬。

## 附三：外部审阅意见的核验结论（2026-09-28）

拿这份项目去问外部 AI 审阅时，收到 19 条建议（4×P0 / 6×P1 / 9×P2）。
**逐条 grep / read 源码核验后才决定是否采纳** —— 结论分三类，错的也记下来：

### A. 属实且采纳（12 条）

| 建议 | 核验结果 |
|---|---|
| 英文色词无词边界，`/red/i` 会命中 `hundred` | **属实，且比说的更严重**：`blueprint`→`#12243Aprint`、`blackberry`、`wooden`、`screaming`(cream)、`rosemary`(rose) 全部误伤。已全表加 `\b` |
| 英文主体抽取失效（全是中文模式） | **属实**，且发现审阅没提到的**语序陷阱**：英文是「图类型 + of/for + 产品」，照搬中文的 `slice(0, 图类型位置)` 会把产品名整段切掉 |
| SSRF：`downloadToGen(url)` 直接 fetch 无校验 | **属实**。已加协议白名单 + DNS 解析后按 IP 判内网 + 禁自动重定向 |
| 词表太薄 | **属实**。已按官方页面重建：疾病表 80+ 条、农药/抗菌、环境声明、自证声明、平台徽章词 |
| 五点引导词规则不该是硬规则 | **属实**。是行业惯例而非平台规则，已 P → C，并放宽正则允许首词后接小写 |
| `BAD_SYMBOLS` 应补注入类符号 | **部分属实**。竖线 / 尖括号 / 反引号确有解析注入风险，已补；`% # = +` **没补**（`100% Cotton`/`Model #A`/`2+1 Pack` 都合法），改用 C7 符号密度规则兜底 |
| `mineKeywords` 应声明不是搜索量 | **属实**，已加 `disclaimer.isSearchVolume=false` 并在界面显示 |
| 无按后台字段导出 | **部分属实**。已有 JSON 导出；真缺的是**逐字段可粘贴**形态，已补 `exportListingFields()`（8 字段，标字符/字节） |
| 品类应差异化 | **属实**。已加 `CATEGORY_CLAIMS`（8 品类），并复用 `detectCategory()` 同一套词表避免漂移 |
| 颜色概念词应上报而非静默跳过 | **属实**。已加 `unrecognized[]`（莫兰迪 / 大地色 / 渐变等 13 条概念正则） |
| `auditPlan` 应校验主体本身是否可用 | **属实**。已加主体健全性检查（`{PRODUCT}` 占位符、中文按 2 计权超 50 报过长） |
| 应支持自定义画幅 | **属实**。已加 `heroRatio` / `pdpRatio` 分组建模 |

### B. 审阅说错了，**没有采纳**（3 条，记下来避免以后再被带偏）

| 建议 | 为什么不做 |
|---|---|
| 「标题应核心词前置、品牌放中段」 | **判断是反的**。亚马逊官方标题公式是 `[Brand] + [Primary Keyword] + [Key Feature] + [Size/Variant]`，且 A9 对品牌前置标题**优先加权**。把品牌后置反而丢掉品牌搜索权重 |
| 「日本站标题按全角字符计数」 | **说错了**。亚马逊官方 FAQ 明确：character-based, not byte-based —— *a 75-character string is 75 characters in any language*。全角按 1 计。⚠️ 真按字节计的只有 **Search Terms** |
| 「完全没有导出能力」 | **不准确**。`index.html` 里已有 `btnExportListing`（导出质检 JSON）。真正缺的是后台字段格式，见 A 组 |

### C. 审阅**完全漏掉**、由本项目自查发现（2 条，都比审阅的多数条目严重）

| 漏掉的 | 为什么严重 |
|---|---|
| **亚马逊主图法规层缺席** | 项目 `hero` 图型写「产品占 35-40% + 留白 45%」，而亚马逊首图硬要求是「占幅 85-100% + 纯白底 + 零叠加」。**两者相加 130%，算术上就不成立**；且 35% 的首图会被直接判不合规。另外 `composePrompt` 原第 8 段会给首图加 `headline at 28-48pt`，与"禁止图内文字"正面冲突。已建独立的 `AMAZON_MAIN_IMAGE` 法规层 + 图位/构图两套口径 |
| **静态服务目录穿越** | `serveStatic` 只挡了 `..`，`GET /.env.local` 就能拿走明文 API Key。叠上 Host 不校验，本机服务可被 DNS rebinding 从任意网页读一遍。审阅只提了 SSRF（出网方向），漏了入网方向 |

> **方法论备注**：审阅意见的价值不在"条数多"，而在"能被源码证实"。
> 这次 19 条里有 3 条是错的、2 条真正严重的问题一条没提。
> 判据很简单 —— **指不出 `文件:行号` 的建议不算证据**。

把本项目跟市面上已有的亚马逊 listing 工具放在一起看，结论是**定位不同**：
成熟方案基本都在做「**抓取 + 生成**」，本项目做的是「**生成 + 合规质检 + 可断言**」。

### 开源同类（GitHub）

| 项目 | 形态 | 关键差异 |
|---|---|---|

### 从对比里得到的三个判断

1. 🔴 **「服务端抓亚马逊」是同类方案最大的公共技术债。**
   `product-listing-ai` 的 README 花了一整段讲怎么跟 "Continue Shopping" 机器人页搏斗 ——
   这恰恰说明这条路脆弱（亚马逊改版即失效）且有 ToS 风险。
   **本项目刻意不服务端抓取**，改用**浏览器书签脚本**：在用户已登录的浏览器里点一下，结构化数据进剪贴板。
   代价是"需要用户点一下"；换来的是**不会被反爬拦、不违反 ToS、不存账号信息**。
2. 🔴 **Multi-Agent 不是这类任务的必需品。**
   二十多条硬约束（字段上限、禁用词、主图法规）靠模型自觉必然漂移；
   `amazon-ai-growth-os` 的 Supervisor 路由增加的是**覆盖面**，不是**可验证性**。
   本项目选确定性流水线，代价是覆盖面窄，换来的是 **469 条可断言**。
3. 🟡 **同类普遍缺「合规质检」这一层，而这正是跨境运营最容易踩的坑。**
   它们多数是 `生成 → 展示` 就结束，把合规留给人肉检查；
   而亚马逊的下架/拒收恰恰来自合规项（疾病声明、农药声明、平台徽章词、HTML 标记）。
   → 本项目把这层做成 28 条带 `why` + `source` 的规则，并**区分硬规则/软规则**（判据是"错了会不会被打"）。

### 顺着这份对比补上的一个真缺口

**竞品关键词覆盖对比** —— `nexscope-ai` 有、之前我们没有。已按本项目的方式补上
（纯函数、零网络、可断言）：`analyzeCoverage()` 逐词检查它落在 **标题／五点／描述／后台词** 哪几处，
并刻意分成两类，避免"报得越多越没人看"：

- `gaps`（**待办**）：**用户自己选的**候选词里，竞品在打、我完全没有 → 优先补进标题或五点
- `minedGaps`（**线索**）：从竞品语料挖出的其他词 —— 含 n-gram 噪声，界面明确写「只当线索看」

覆盖度用**字段权重 3/2/1/1**（标题/五点/描述/后台词）算，并标注这是**行业通行做法、不是官方明文**；
界面与导出的免责声明都写明「这是文本覆盖，不是搜索排名、不是搜索量」。

⚠️ **明确不做的三件事（想清楚才不做，不是没想到）**：
① 不接付费关键词 API（搜索量数据要花钱，与"零门槛"定位冲突）；
② 不做服务端抓取（同第 1 条）；
③ 不做多站点选择器的持续维护（亚马逊改版即失效，维护成本无底）。

### "好用好上手"这一点的具体落点

需求原话里"**确保功能真正好用好上手**"这句，落到具体设计上是四条：

1. **最短路径只有 3 步**：① `npm start` → ② 浏览器打开 `http://127.0.0.1:8787`（页面顶部的告警条会把这一步说清楚）→ ③ 拖一次书签。
2. **每个"没数据"的地方都要说清原因**：显示 `—` 而不是 `0`，并注明为什么算不出来（沿用法则 5：**宁可给"算不出来"，不给假数字**）。
3. **一键闭环优先于"多一个选项"**：整页采集 → 一键当竞品 → 一键对比 → 一键把共识词填入关键词框。每一步都能一步接下一步，用户不需要记"该先去哪个页面"。
4. **降级必须响亮**：识图失败会让参考图**真的没被参考**，所以它必须发一条 `warn` 级别的可见事件（原来只发一行 tool_result，用户以为正常）—— 静默降级比报错更伤人。
